Security

ProxyGate stays small and local-first: one binary, one config file, sensible defaults. This page explains what those defaults protect, what they don't, and the settings that lock an installation down further.

DEFAULT on out of the box OPT-IN advanced setting CLI run on the machine

Overview

ProxyGate has two sides with very different exposure.

MODEL Threat model who reaches what, and what protects it
SideWho reaches itWhat protects it
ProxyAnyone on the internet, on http_port and https_portTLS and header timeouts. It only forwards to the targets you configured.
Admin UI and APIYou, on admin_portNetwork allowlist, login, and optionally HTTPS.

The admin side can change routes, issue certificates and edit DNS records, so it is treated as privileged. Anyone who can read or write ProxyGate's data directory as the service user, or as root, is trusted: that is how password recovery works, and no setting on this page protects against that level of access.

Defaults

These apply with no configuration.

DEFAULT Admin login required every API call and the live event stream

Every /api/* endpoint and the live event stream need a signed-in session or an API token. /healthz and /docs/ stay public, and the UI's static files load so the sign-in page can show.

DEFAULT First start locked until you set a password

No password exists yet, so the admin UI is locked. ProxyGate writes a one-time setup code to data/setup-code, readable by the service user only, and logs where the file is, never the code itself. Open the admin UI, enter the code and choose a password. The file is deleted once used.

DEFAULT Sessions 12h idle · 7 days max

HttpOnly, SameSite=Strict cookie, also Secure over HTTPS, with a new session ID at every sign-in. Sessions end after 12 hours without activity or 7 days in total, on sign-out, and for every browser when the password changes. They are kept in memory, so restarting ProxyGate signs everyone out.

DEFAULT Failed sign-ins 5 attempts per 15 minutes

Five failures from one address within 15 minutes block further attempts from it until the 15 minutes are up. Setup and password changes count the same way.

DEFAULT Password storage argon2id

Hashed with argon2id using OWASP's recommended parameters (46 MiB, 1 iteration, 1 thread) in data/admin-auth.json, separate from proxygate.json. The minimum is 8 characters unless strong rules are chosen.

DEFAULT Plain-HTTP warning shown on the sign-in page

When the sign-in page is served over plain HTTP to anything other than localhost, it warns that the password crosses the network unencrypted. A VPN or an SSH tunnel already encrypts the connection, so the warning can be ignored there. To refuse such logins instead, see require_secure_login.

DEFAULT API tokens for scripts · only hashes stored

Scripts call the API with Authorization: Bearer <token>. Tokens are managed on the machine rather than in the UI, and only a SHA-256 hash of each one is stored.

proxygate token create backup-script --config ./data/proxygate.json   # prints the token once
proxygate token list --config ./data/proxygate.json
proxygate token revoke backup-script --config ./data/proxygate.json
DEFAULT Encrypted credentials GoDaddy key, secret, ACME email · AES-256-GCM

The key comes from PROXYGATE_CONFIG_KEY when it is set (64 hex characters, for example from openssl rand -hex 32). Otherwise ProxyGate creates data/secret.key with mode 0600 the first time it stores a credential. Existing plaintext configs are encrypted the next time ProxyGate starts.

This protects the config file when it travels on its own: in a backup, a commit, or a paste into an issue. It does not protect against someone who can read the data directory, because the key file is there too. Keep secret.key out of backups that leave the machine, or set PROXYGATE_CONFIG_KEY from somewhere else.

If the key is missing or wrong, ProxyGate still starts and serves every route. The credentials are treated as empty, the encrypted values stay in the file untouched, and the admin UI shows what happened. Enter them again, or restore the key and restart.

TLS private keys in certs/ are plain files readable only by the service user, as with other web servers.

Operations

Tasks run on the machine where ProxyGate is installed.

CLI Recovering access proxygate passwd

Anyone who can act as the service user on the machine can set a new password:

sudo -u proxygate proxygate passwd --config /opt/proxygate/data/proxygate.json

# or print a random password instead of typing one:
sudo -u proxygate proxygate passwd --config /opt/proxygate/data/proxygate.json --generate

This signs out every browser. The running server picks up the new password on the next request; no restart is needed. Run as root, the command keeps the credentials file owned by the user that owns the config, so the service can still read it.

CLI Upgrading from an earlier version routes keep serving

On first start the admin UI locks until a password is set with the one-time code, scripts that call the API need an API token, and stored credentials are encrypted with a new data/secret.key. Earlier versions can still read that config if started with PROXYGATE_CONFIG_KEY=$(cat data/secret.key).

The deployment guide has the full upgrade and rollback steps.

Advanced settings

These live in the security section of proxygate.json and take effect after a restart. Leave them out to keep the defaults.

"security": {
  "admin_tls": { "enabled": true, "cert_file": "", "key_file": "" },
  "require_secure_login": true,
  "session_idle_timeout": "2h",
  "session_max_age": "24h",
  "encrypt_secrets": true
}
OPT-IN admin_tls default: off

Serve the admin UI and API over HTTPS. Set cert_file and key_file to use your own certificate. When they are empty, ProxyGate creates a self-signed certificate in data/ covering localhost, the machine's hostname and its current IP addresses, and logs its SHA-256 fingerprint so you can compare it with the one your browser shows.

OPT-IN require_secure_login default: false

Refuse setup, sign-in and password changes unless the connection is HTTPS or comes from localhost.

OPT-IN session_idle_timeout · session_max_age defaults: 12h · 168h

Sign out after this long without activity, and after this long regardless of activity. Values use Go duration syntax such as "30m", "2h" or "24h".

OPT-IN encrypt_secrets default: true

Set to false to store the GoDaddy credentials and ACME email in plaintext. Values that are already encrypted are still decrypted.

OPT-IN Strong password rules chosen at first setup

A checkbox on the setup screen, or proxygate passwd --policy strong. Requires at least 12 characters and rejects very common passwords and passwords containing "proxygate", following NIST SP 800-63B, which favours length and a blocklist over forced character classes. The choice applies to every later password change; proxygate passwd --policy basic relaxes it again.

The network allowlist (server.allowed_networks) and the admin address (server.admin_host, 127.0.0.1 by default) remain the first line of defence.

Guidance

Recommendations and what's coming.

GUIDE Suggested hardening for an installation reachable from more than one machine
  1. Keep admin_host on 127.0.0.1 and reach the UI over an SSH tunnel or a VPN, or enable admin_tls and require_secure_login.
  2. Allow only the addresses that need the UI in allowed_networks.
  3. Choose strong password rules at setup.
  4. Set PROXYGATE_CONFIG_KEY from your service manager instead of relying on data/secret.key.
  5. Give ProxyGate DNS credentials with no more access than you are comfortable with. GoDaddy API keys cover the whole account, and scoping that is up to you, for example by delegating _acme-challenge records to a zone you can restrict.
PLANNED Roadmap not yet implemented
  • Two-factor authentication: TOTP first, then passkeys (WebAuthn needs the admin UI on HTTPS or localhost).
  • Stronger secret storage: systemd credentials (LoadCredentialEncrypted, TPM-backed where available) on systemd hosts.
  • Audit log: an append-only record of admin changes with time, address and what changed.
  • Dependency scanning: govulncheck in CI, and updating github.com/gorilla/websocket past advisory GO-2026-6278 and golang.org/x/crypto past v0.31.0.
